# Action Routing

Read this reference before proposing downstream work. A meeting can justify up
to five action categories, but each useful outcome has one authoritative home.
Do not mirror work across systems or manufacture an action to fill the bundle.

## Use only supported action categories

Evaluate these categories independently for each newly proposed meeting:

1. **Meeting note:** the refined durable record in the configured approved-note
   source.
2. **Task or issue:** new work or a material update to existing work in its
   canonical task or issue system.
3. **Durable context:** a material change to an existing person, project,
   strategy, customer-research, decision, or learning record.
4. **Calendar:** a selective block for ready work that warrants reserved human
   attention.
5. **Communication draft:** complete editable text for a possible message; it
   is not permission to send.

Omit a category when evidence does not support a useful change. Keep every
proposed action independently approvable, even when one action depends on
another. Do not combine two external effects merely because they came from the
same meeting.

Completion: every included category has a supported independent effect, and no
empty category appears.

## Resolve the canonical destination

Inspect current context and existing work before proposing a create or update.
Use stable identifiers and authoritative search where available; a similar
title alone does not prove equivalence.

Load the configured ownership map from the user's authoritative guidance. Keep
product and repository work in its established issue system. Keep personal,
relationship, administrative, and cross-system commitments in the configured
task system. When one system mirrors another, use the upstream owner rather
than its synchronized copy.

Do not copy issue-owned work into another task system. A separate task is
justified only when the user has a distinct personal commitment not represented
by the canonical issue. A meeting-note link to an issue is context, not a
second task. When the ownership map is unavailable or ambiguous, leave the
ambiguity in the meeting review and omit that action until ownership is
resolved instead of choosing a provider.

When an applicable canonical task or issue workflow is available, use it for
schema, context inspection, duplicate checks, approval, and readback. Such a
companion workflow is an optional capability, not a package dependency. If no
safe write path exists, preserve the proposal and classify application as
**Manual** rather than changing the destination or claiming success.

Completion: every proposed task or issue has one owning system and one checked
target or creation destination.

## Keep other people's promises in context

Record another person's promise in the meeting note. Do not turn it into a task
for the user unless it creates a meaningful dependency on an outcome the user
owns. When that dependency is worth tracking, propose one task in the
configured task system using its explicit waiting state, with:

- the verified person or event being awaited;
- the user-owned outcome that depends on it; and
- a real follow-up date supported by the meeting or explicitly chosen during
  review.

Do not invent a follow-up date, assign the other person's work to the user, or
track a merely interesting promise as an obligation.

Completion: nonblocking promises remain meeting context, while meaningful
dependencies have one honest waiting record.

## Change durable context selectively

Propose a person, project, strategy, customer-research, decision, or learning
record change only when the meeting materially changes what that record should
say. Link a record only after an unambiguous match. Propose a new person record
only when an ongoing relationship or follow-up needs durable identity.

State the new fact or precise edit. Do not copy the meeting summary into several
records, promote every observation into a learning, or guess a link for an
unresolved identity.

Completion: each context proposal adds a durable fact that belongs in exactly
one named record.

## Route companion relationship effects

Use `managing-personal-crm` in embedded mode for relationship identity,
contact, durable meaning, contextual relevance, and duplicate judgment. Keep
the meeting workflow in charge of one proposal and one action bundle.

Route the companion's outputs through existing categories. Contact-date and
Person-prose changes become separate durable-context actions. A dated personal
follow-up goes to the configured canonical relationship task system, while
unrelated product or repository work stays in its established issue system.
Communication uses the existing draft category. Contextual insight may remain
in the proposal without creating a destination effect.

When the companion is unavailable, complete ordinary meeting review. Omit a
relationship guess, or mark a clear effect **Manual** when no safe application
path is available.

Completion: every companion output has one meeting-owned action category and
canonical destination, or remains a non-durable insight.

## Reserve calendar time selectively

Propose a time block only when the work is ready, needs human attention, and
has enough urgency, strategic value, or focus demand to justify reserved time.
Do not propose a block for agent-only, quick, unready, speculative, or low-value
work.

Use capability roles rather than embedding private account identifiers:

- configured work-product tasks use the configured work calendar;
- personal work uses the configured personal calendar.

The event links to the canonical task or issue, and that item retains the event
identity or link when its interface supports a backlink. A block that needs a
new or updated task or issue declares that action as a prerequisite. If the
calendar is full, name the concrete tradeoff rather than silently moving a
fixed meeting or changing a real deadline. Rescheduling work time does not
change the task's deadline.

Completion: every proposed block protects worthwhile ready work, names its
calendar and canonical work item, and exposes any tradeoff or dependency.

## Keep communications as drafts

A communication proposal contains complete editable text plus the acting
identity, recipients, thread or destination, and reason. Text displayed in the
review bundle is a draft suggestion, not an external draft object and not a
send authorization.

The meeting workflow keeps the draft in the conversation. Creating an external
draft object or sending a message belongs to a later, explicit communication
request and its configured workflow; approval here never authorizes either.

Route consequential operations such as payments, refunds, production changes,
or destructive calendar changes to canonical work or mark them **Manual**.
Do not execute them as meeting follow-up side effects.

Completion: communication remains editable and unsent, and consequential work
has an explicit owner outside this workflow.
